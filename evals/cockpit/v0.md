# Dashboard v0, the cockpit: shown failing, then running

Milestone 2a.10 in [docs/ROADMAP.md](../../docs/ROADMAP.md): on localhost, live decisions from the record, spend against
caps, intents, the latch and the Squads limit remaining; every chain read opts in to v1
([ADR-011](../../design/ADR-011-phantom-roles-and-dashboard.md)). Run on 2026-10-01 with Node 26.7.0 and Chrome 153,
headless.

| File | What it is |
|---|---|
| `packages/sdk/src/inspect.ts` | `inspectRecord(entries, policy)`: the view, computed as a restore rebuilds the guard |
| `apps/cockpit/src/server.ts` | `npm run cockpit -- --record … --policy … [--rpc … --squads …]` |
| `apps/cockpit/src/page.html`, `cockpit.js`, `cockpit.css` | the page; everything drawn with `textContent` |
| `apps/cockpit/src/demo.ts`, `screenshot.ts` | a demo record, and the screenshot below |
| `packages/sdk/test/inspect.test.ts`, `apps/cockpit/test/cockpit.test.ts` | 3 and 6 tests |

**What makes it safe to leave running.** It binds 127.0.0.1. It answers only requests addressed to `127.0.0.1` or
`localhost` (421 otherwise), so a page on another site cannot reach it through a rebound DNS name. It takes GET only,
and holds no keys. It reads three things: the record, the policy, and public chain data. Its page has a content
security policy with no inline script and no inline style.

**What it shows is the guard's own view.** `inspectRecord` applies the record exactly as a restore does, so the
cockpit cannot disagree with what the guard will do next.

## 1. Failing first

- `inspect.test.ts` against a stub: `ℹ tests 3   ℹ pass 0   ℹ fail 3`. The first real run failed one test, and the test
  was wrong: it counted every pending attempt as in flight. The guard's rule is "could still land", which excludes an
  attempt whose last valid height has passed. The test now applies that rule.
- `cockpit.test.ts` against a stub: `ℹ tests 6   ℹ pass 0   ℹ fail 6`. The first try hung, which was a test-hygiene bug:
  when the stub threw, the test's own stand-in RPC server was never closed, and the runner waited on it. Every server
  in the tests now closes in a `finally`.

## 3. Running, with a chain behind it

[runs/2026-10-01-cockpit-v0.png](../../runs/2026-10-01-cockpit-v0.png). The record comes from `demo.ts`; the chain is a
local validator holding Squads v4's devnet program, with a limit kept in place by
`apps/onchain/src/squads.ts --keep`. The page shows:
- **The latch banner:** latched at decision 9.
- **Spend against the caps:** SOL 0.025 of 0.2 in the hour, fees 0.00002 of 0.01.
- **The Squads limit:** 0.01 of 0.02 SOL spent today, the agent's key and the one destination. The agent's own
  transactions are listed with their results: two refused by the program, two landed.
- **The decision stream:** each verdict with its rule, Keel's posture and the three numbers.
- **The intents,** one still in flight.

**What the demo found.** The demo record was meant to show a normal stream, and it latched instead.
- **The proposal.** An agent re-sent a payment whose outcome was still unknown. The re-send was rightly denied as
  `intent-in-flight`.
- **The latch.** The same proposal met Keel's REGROUND. Its repetition was 1, a retry of an unlanded intent, and
  valence was already at -0.4 from one earlier denial and the unknown outcome. The spec latches on any REGROUND, so
  one re-send stopped the guard.
- **What it means.** That latch protects against double-sends, and may also be heavy-handed for a single retry. It is
  an open question in [docs/SPEC.md](../../docs/SPEC.md) §12, not a change made here.

## 4. What is not achieved yet

- **The chain panel has run against a local validator only.** 2a.10 depends on 2a.9, whose devnet run waits for

  pointed at devnet and photographed again.
- **No operator actions.** Releasing the latch from the cockpit, through Phantom, is milestone 3.8.
