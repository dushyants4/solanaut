1. **Vendor the office, don't install it.**
   - **What gets copied:** the seven seats from office-core `182b7a9`; the guard from office `main`
     (with its fail-open and seat-gate fixes); and the six SOPs.
   - **Renamed:** marketplace `solanaut-office`, plugins `solanaut-<seat>`.
   - **Recorded:** both commits, in `plugins/VENDORED.md`.
   - **Not copied:** the APEX runs, `deploy/`, the harvest `kb/`, the release gate, and the APEX
     policy.
   - **Why:** installing office-core would import APEX context and its old guard. It would also
     collide with the global `office` marketplace name.
2. **Isolation in five layers.**
   - **(a) Location:** a sibling folder, with no shared ancestor instructions.
   - **(b) Plugins:** `Solanaut/.claude/settings.json` sets all 34 Gubernaut plugins to `false`, and
     enables only the Solanaut seats.
   - **(c) The guard:** a Solanaut `boundaries.toml` enforced by the guard, as a project hook:
     - deny writes into the APEX tree, `~/Work/`, `~/.claude/` (except this project's own memory
       folder) and `Docs-Dashy-Drop/`;
     - deny `.env` and key-shaped files everywhere.
   - **(d) Own state:** its own git and remote, its own Codex trust entry, its own Chrome profile,
     and a project-local Solana config (every script passes `--url` and `--keypair`; the global
     `~/.config/solana` is never touched).
   - **(e) Gubernaut only as a published dependency:** `@gubernaut/core@1.0.1` from npm, its
     wasm digest checked at load, and its public docs by URL. No path into APEX.
3. **An honest architecture.** Two defences, each doing what it can actually do:
   - **Deterministic transaction policy:** program and destination allowlists, and per-transaction
     and per-window caps. It lives outside the model, so nothing the model says can change it. This
     is the injection defence.
   - **Keel's control loop on telemetry derived from transactions:** repetition of near-identical
     proposals, value against caps, and failure streaks. This handles retry loops and fee
     escalation.
   - Both decisions go into a local log, which on-chain becomes events.
4. **Claims discipline carries over.**
   - `docs/CLAIMS.md` lists what Solanaut may say and its source. Gubernaut figures are quoted as
     "Gubernaut reports…" with their scopes.
   - Every drop-doc claim is triaged there: kept, reframed or rejected.
5. **Build in the dedicated Solanaut session.**
   - This session does the setup, a first runnable slice, the remote and the Colosseum entry.
     Nothing more.
   - Afterwards APEX never writes into Solanaut, apart from splitting the plan file in step 0.

## Architecture: long term (goes to `docs/ARCHITECTURE.md`)

```
agent (ElizaOS / AgentKit / any code) ── proposes tx ──▶ @solanaut/sdk  guard.evaluate(tx)
   policy  (allowlists, caps, windows)        → DENY with reason, whatever the model said
   sensor  (tx → intensity, valence, repetition)
   Keel    (@gubernaut/core, digest-checked)  → DEFAULT / INHIBIT / REGROUND → hold / stop
   decision log (JSONL; on-chain via the vault program)
          │ ALLOW → sign → RPC            │ DENY → never signed, error returned (no silent retry)
Adapters:  @solanaut/plugin-eliza · AgentKit wrapper · solanaut-rpc-proxy (non-JS stacks)
On-chain:  programs/solanaut_vault (Anchor): spending policy enforced by the program, plus
           emit! events carrying the decision, the telemetry and the posture
Apps:      apps/sandbox (the plugin sandbox) · apps/cockpit (web: live decisions on devnet)
```

The sensor is the genuinely new work, and it is measured, not assumed. The "fail closed"
rule applies throughout: a guard error, a boundary rejection, or a digest mismatch means DENY.
